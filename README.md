# 스폰지밥 캐릭터 탐지 및 추적
YOLOv8을 fine-tuning하여 스폰지밥, 뚱이, 징징이를 탐지하고, ByteTrack으로 영상 속 캐릭터를 추적한 기계학습 과제입니다.

| 데이터 | 모델 | 추적 |
|---|---|---|
| 3개 클래스 · 이미지 357장 | YOLOv8n | ByteTrack |

**[결과 영상](비키니시티.mp4) · [학습한 모델](best.pt)**

---

## 1. 과제 소개

이번 과제는 3개 부류의 데이터를 수집하고, YOLO 모델을 fine-tuning한 결과를 제출하는 과제입니다.

탐지 대상으로는 제가 좋아하는 애니메이션의 캐릭터인 스폰지밥, 뚱이, 징징이를 선택했습니다. 유튜브 애니메이션 영상을 직접 녹화하고 이미지를 추출하여 데이터셋을 만들었습니다. 이후 라벨링과 학습을 진행하고, 다른 에피소드의 영상에 모델을 적용했습니다.

스폰지밥 캐릭터를 탐지하도록 만들어진 기존 모델을 사용하지 않았습니다. 일반 객체 탐지용으로 사전 학습된 `yolov8n.pt`를 불러와, 직접 구성한 데이터로 fine-tuning했습니다.

캐릭터마다 종류와 위치를 표시했습니다. 한 이미지에 여러 캐릭터가 등장하는 경우에는 각각의 캐릭터에 박스를 부여했습니다.

|---|---|---|

## 3. 데이터 형식 변환

Roboflow에서 다운로드한 데이터는 COCO 형식이었습니다. 이를 YOLO 학습에 사용할 수 있도록 변환했습니다.

- 클래스 ID를 `0`, `1`, `2`로 변경
- 박스 좌표를 중심 좌표, 너비, 높이로 변환
- 이미지 크기를 기준으로 좌표 정규화
- 이미지별 TXT 라벨 파일 생성
- 데이터 경로와 클래스 이름을 담은 `data.yaml` 작성

YOLO 라벨 파일의 각 줄은 다음과 같습니다.

```text
클래스_ID 중심_x 중심_y 너비 높이
```

변환한 데이터는 다음 구조로 구성했습니다.

```text
spongebob_yolo/
├── train/
│   ├── images/
│   └── labels/
├── valid/
│   ├── images/
│   └── labels/
├── test/
│   ├── images/
│   └── labels/
└── data.yaml
```

변환 후에는 학습 이미지 일부에 박스와 클래스 이름을 표시하여 위치와 이름이 맞는지 확인했습니다.

원본 COCO 데이터와 YOLO 변환 데이터는 별도로 보관했습니다. 데이터셋은 이 저장소에 포함하지 않았습니다.

## 4. 모델 학습

### 학습 환경

| 항목 | 내용 |
|---|---|
| 실행 환경 | Google Colab |
| GPU | NVIDIA Tesla T4 |
| Python | 3.13.16 |
| PyTorch | 2.14.1+cu130 |
| Ultralytics | 8.4.215 |

### 학습 설정

| 항목 | 설정 |
|---|---|
| 모델 | YOLOv8n |
| 초기 가중치 | `yolov8n.pt` |
| Epochs | 50 |
| 이미지 크기 | 640 |
| Batch size | 16 |
| Patience | 10 |
| Seed | 42 |

Roboflow에서 데이터를 내보낼 때 별도의 전처리나 증강은 적용하지 않았습니다. 학습에서는 아래에 지정한 값 외에 Ultralytics의 기본 설정을 사용했습니다. 따라서 Roboflow의 증강 설정과 학습 중 적용되는 증강은 구분해야 합니다.

### 학습 코드

```python
from ultralytics import YOLO

model = YOLO("yolov8n.pt")

model.train(
    data="/content/spongebob_yolo/data.yaml",
    epochs=50,
    imgsz=640,
    batch=16,
    patience=10,
    device=0,
    workers=2,
    seed=42,
    project="/content/spongebob_runs",
    name="yolov8n_finetune",
    plots=True,
    save=True
)
```

총 50 epoch의 학습을 완료했습니다. 검증 성능을 기준으로 선택된 `best.pt`를 최종 평가와 영상 처리에 사용했습니다.

`last.pt`는 마지막 학습 시점의 모델이며, 이번 결과에 사용한 모델은 `best.pt`입니다.

## 5. 테스트 결과

학습을 마친 뒤 Test 이미지 **36장**, 정답 박스 **52개**를 대상으로 평가했습니다.

### 전체 성능

| 지표 | 결과 |
|---|---:|
| Precision | 88.01% |
| Recall | 89.44% |
| mAP@0.5 | 90.44% |
| mAP@0.5:0.95 | 78.52% |

- **Precision:** 모델이 탐지한 결과 중 정답으로 인정된 비율
- **Recall:** 실제 객체 중 모델이 찾아낸 비율
- **mAP@0.5:** 예측 박스와 정답 박스의 IoU 기준을 0.5로 두고 계산한 클래스별 AP의 평균
- **mAP@0.5:0.95:** IoU 기준을 0.5부터 0.95까지 0.05 간격으로 적용한 mAP의 평균

IoU는 예측 박스와 정답 박스가 얼마나 겹치는지를 나타냅니다. 기준이 높을수록 박스 위치까지 더 정확하게 맞춰야 합니다. 따라서 mAP를 단순한 정답률로 해석하지 않았습니다.

### 클래스별 성능

아래 수치는 클래스별 평가 로그에 출력된 반올림 값을 기준으로 작성했습니다.

| 캐릭터 | 정답 박스 수 | Precision | Recall | AP@0.5 | AP@0.5:0.95 |
|---|---:|---:|---:|---:|---:|
| 뚱이 | 20 | 93.9% | 95.0% | 98.8% | 88.3% |
| 스폰지밥 | 17 | 97.3% | 100.0% | 99.5% | 88.5% |
| 징징이 | 15 | 72.9% | 73.3% | 73.0% | 58.8% |

### 결과 해석

뚱이와 스폰지밥은 이번 테스트에서 높은 성능을 보였습니다. 반면 징징이는 Precision과 Recall이 모두 낮았습니다. 징징이를 잘못 탐지하는 경우와, 실제로 등장했지만 놓치는 경우가 모두 있었습니다.

징징이는 AP@0.5:0.95도 상대적으로 낮아 박스 위치의 정확도 역시 확인할 필요가 있습니다. 다만 이번 결과만으로 성능 차이의 원인을 단정할 수는 없습니다. 실패한 이미지의 자세, 가림 정도, 객체 크기와 라벨을 살펴봐야 합니다.

또한 테스트에 포함된 징징이의 정답 박스는 15개입니다. 표본이 적기 때문에 이 수치만으로 다른 영상에서도 같은 성능이 나온다고 판단하기는 어렵습니다.

## 6. 영상 탐지 및 추적

학습 데이터를 수집한 영상들과 **다른 에피소드**에 모델을 적용했습니다.

| 항목 | 내용 |
|---|---|
| 원본 영상 | [유튜브 영상](https://youtu.be/I-Lbv_lYEnQ) |
| 사용 구간 | 28분 39초부터 5초간 |
| 탐지 모델 | `best.pt` |
| 추적 알고리즘 | ByteTrack |
| 결과 파일 | `비키니시티.mp4` |

6초 길이로 준비한 영상에 탐지와 추적을 적용한 뒤, 앞부분 5초를 제출용으로 저장했습니다.

### 결과 영상

**[탐지·추적 결과 보기](비키니시티.mp4)**

영상에는 캐릭터의 위치를 나타내는 박스, 클래스 이름, 신뢰도, 추적 ID를 표시했습니다.

YOLOv8은 각 프레임에서 캐릭터의 종류와 위치를 예측하고, ByteTrack은 프레임 사이의 탐지 결과를 연결해 ID를 부여합니다.

### 실행 예시

```python
from ultralytics import YOLO

model = YOLO("best.pt")

results = model.track(
    source="input_video.mp4",
    tracker="bytetrack.yaml",
    conf=0.25,
    imgsz=640,
    device=0,
    stream=True,
    save=True
)

for result in results:
    pass
```

`input_video.mp4`를 적용할 영상의 경로로 변경하면 됩니다. GPU가 없는 환경에서는 `device=0`을 `device="cpu"`로 변경해야 합니다.

제출 영상은 노트북에서 프레임별 결과를 저장한 뒤, 재생 가능한 MP4 형식으로 변환하고 5초로 잘랐습니다.

### 추적 ID 확인

영상을 확인하는 과정에서 장면이 바뀐 뒤 ID가 새로운 번호로 바뀌는 현상이 있었습니다.

추적 ID는 캐릭터 종류에 고정된 번호가 아닙니다. 예를 들어 뚱이가 항상 `id:1`을 갖는 것은 아닙니다. 장면 전환으로 기존 추적이 끊기면 같은 캐릭터에도 새로운 번호가 붙을 수 있습니다.

이번 영상에서는 캐릭터의 이동이 크지 않았습니다. 따라서 빠른 이동이나 긴 가림 상황에서 추적이 얼마나 유지되는지까지 확인한 것은 아닙니다.

## 7. 한계와 보완할 점

### 유사한 프레임이 포함될 가능성

이미지를 5초 또는 10초 간격으로 추출했지만, 같은 장면이 이어지면 비슷한 이미지가 포함될 수 있습니다. 추출 간격을 두었다고 해서 학습·검증·테스트 간 장면 중복이 없어지는 것은 아닙니다.

이후에는 장면이나 에피소드 단위로 데이터를 나누어 평가할 필요가 있습니다.

### 징징이 데이터 점검

전체 평균만 보면 클래스별 성능 차이가 잘 드러나지 않습니다. 이번에는 징징이의 성능이 상대적으로 낮았으므로, 징징이의 실패 사례를 먼저 확인하고 부족한 유형의 학습 이미지를 추가할 필요가 있습니다.

### 영상 평가 범위

다른 에피소드에서 탐지·추적 결과를 확인했지만, 5초 영상만으로 다양한 상황에서의 성능을 판단하기는 어렵습니다. 이후에는 이동, 가림, 재등장이 포함된 장면에서도 확인할 필요가 있습니다.

영상 결과는 직접 재생하며 확인했고, 별도의 추적 성능 지표는 계산하지 않았습니다. **5번의 mAP는 결과 영상이 아니라 Test 이미지 36장에서 계산한 값입니다.**

## 9. 실습을 마치며

처음에는 스폰지밥, 뚱이, 징징이를 구글링해서 각각 100장씩 모으려고 했었으나, 수집과 라벨링에 걸리는 시간을 고려해, 영상에서 일정 간격으로 이미지를 추출하고 자동 라벨링 후 직접 확인하는 방식으로 진행했습니다.

학습 결과를 확인했을 때는 전체 mAP보다 징징이의 낮은 성능이 먼저 눈에 들어왔습니다. 전체 수치만 확인하는 것과 클래스별 결과를 나누어 보는 것은 차이가 있었습니다.

또한 영상에서 ID가 1, 2, 3 다음에 5로 표시되어 처음에는 문제가 있는 줄 알았습니다. 확인해 보니 장면 전환 이후 새 ID가 붙은 것이었고, 이 과정에서 클래스 번호와 추적 ID의 차이를 이해할 수 있었습니다.

직접 모은 이미지로 학습한 모델이 다른 에피소드에서도 캐릭터를 탐지하는 것을 확인했습니다. 다만 결과 영상이 잘 나온 것과 여러 상황에서 안정적으로 작동하는 것은 구분해야 한다고 생각했습니다.
